## Dependency notes

- **011** (CI) requires **009** (lint) and **010** (tests) because the CI workflow
  runs `pnpm lint` and `pnpm test`; those scripts must exist first.
- **001–008** are independent of each other and can land in any order, but the
  recommended order maximizes risk reduction first (security → correctness → debt).
- **010** (tests) is listed P1 because it unblocks safe execution of every other
  plan: once it lands, later plans can add regression tests as a done-criterion.
  It is sequenced after the security/correctness fixes only so those fixes don't
  wait on test scaffolding — land 010 early if you prefer test-first.
- **012** (proxy) is low urgency on Next 15.5 (middleware is not yet deprecated);
  it becomes required when upgrading to Next 16.

## Findings considered and rejected

- **`z.string().datetime()` vs the booking form**: not a bug. The client sends
  `new Date(...).toISOString()` (`app/mis-turnos/nuevo/page.tsx:122`), which is
  valid ISO-8601 UTC that `z.string().datetime()` accepts. (The _timezone_ issue
  in plan 002 is a different, real problem.)
- **reCAPTCHA field-name mismatch** (`g-recaptcha-response` vs `recaptcha_token`):
  not a bug in the live flow. The booking form submits via the Server Action
  (`app/register/actions.ts`), which reads `g-recaptcha-response` correctly. The
  `recaptcha_token` name only appears in the unused API route — folded into
  plan 008 (dead code) and plan 001 (the bypass that route shares).
- **Role/ownership authorization**: audited across every route handler
  (`app/api/**`); admin-vs-client checks and per-row ownership checks are present
  and consistent. No IDOR found. Not planned.
